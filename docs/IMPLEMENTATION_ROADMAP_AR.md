# خارطة تنفيذ SUCA OS Mobile

## الغرض

تحويل خطط SUCA التقنية إلى مراحل تنفيذية قابلة للفحص، مع الحفاظ على سلامة الجهاز الحقيقي وعدم تعديل boot.img الأصلي أو إعلان دعم جهاز قبل اختبار مكوناته الأساسية.

## مسارات التنفيذ

| المسار | الناتج |
|---|---|
| تعريف الأجهزة | ملف profile مستقل لكل جهاز يصف kernel وDTB والذاكرة والشاشة والطاقة والعتاد |
| HAL | واجهات موحدة للبطارية والشاشة واللمس والصوت والكاميرا والمودم والحساسات |
| التحديث | metadata موقعة، تحقق SHA256، نشر مرحلي، A/B، health check، rollback |
| Recovery | فحص boot state، استعادة النسخ، الرجوع إلى slot سابق، سجل أعطال |
| التطبيقات | فصل الواجهة عن الخدمات، حالات عدم التوفر، migrations، تحديث APK مستقل |
| الأمان | Permissiond، D-Bus، Polkit، أقل صلاحية، عزل التطبيقات |
| الاختبارات | اختبارات بنية، اختبارات واجهة، اختبارات خدمات، مصفوفة جهاز، تشغيل غير تدميري |
| المنتج | توثيق الدعم، خدمات porting، حزم مؤسسات، مواد تعريفية دون ادعاءات تجارية غير مثبتة |

## ترتيب التنفيذ الإلزامي

1. تثبيت مواصفة Device Profile.
2. إضافة SM-A135F كجهاز مرجعي دون تعديل صورة الإقلاع الأصلية.
3. تعريف مستويات الدعم من boot-only إلى daily-driver.
4. فصل واجهات HAL عن تفاصيل Exynos أو Samsung.
5. إنشاء مصفوفة توافق قابلة للتحديث.
6. تعريف عقود تحديث النظام والتطبيقات.
7. تعريف نموذج A/B وBoot State وRecovery.
8. إضافة سياسة توقيع وSHA256 ورفض الأجهزة غير المتوافقة.
9. ربط التطبيقات بالخدمات بدل الوصول المباشر إلى root أو العتاد.
10. إضافة اختبارات حالات عدم توفر المودم والكاميرا والصوت.
11. بناء حزم APK قابلة للتكرار ومراجعة اعتمادياتها.
12. اختبار كل مرحلة في بيئة محاكاة قبل تجربة الهاتف.
13. توثيق النتيجة بحسب الجهاز والإصدار ورقم البناء.
14. إعلان مستوى الدعم الفعلي فقط.

## مستويات دعم الجهاز

| المستوى | الوصف |
|---|---|
| `boot-only` | kernel وramdisk يصلان إلى userspace |
| `basic-ui` | شاشة ولمس وWayland وSUCA Shell |
| `usable` | تخزين وطاقة وصوت وشبكة وإدخال مستقر |
| `hardware` | كاميرا ومودم وBluetooth وحساسات تعمل |
| `daily-driver` | نوم عميق، استيقاظ، تحديث A/B، Recovery، اختبارات طويلة |

## سياسة السلامة

لا يُكتب إلى boot أو system أو vendor أثناء الاختبارات الآلية. تُفحص الصورة منفصلة، ويُحفظ الأصل، وتُستخدم بيئة Termux/Alpine/proot أو Xvfb لاختبار الأجزاء التي لا تحتاج إلى عتاد. لا تُعتبر نتيجة بناء أو تشغيل واجهة دليلًا على عمل المودم أو الكاميرا.

## معيار الإنجاز

لا تنتقل ميزة من حالة «هيكل» إلى «مدعومة» إلا إذا كان لها مصدر، عقد واضح، اختبار ناجح، سجل نتيجة، ووصف لمتطلبات العتاد. ولا تنتقل من «مدعومة» إلى «مستقرة» إلا بعد اختبار إعادة التشغيل، فشل الخدمة، انقطاع الشبكة أو الطاقة، واستعادة الحالة السابقة.
